# المدقق المحاسبي للموبايل

تطبيق Flutter مستقل لـ Android وiOS باستخدام GetX وMVC وبروتوكول الموقع 1. جميع الإضافات داخل mobile_app؛ لم تُعدّل ملفات السيرفر.

## التشغيل

```powershell
cd 'D:\ALMIZAN NEW\mobile_app'
flutter pub get
flutter analyze
flutter test
flutter run -d <android-device-id>
flutter build apk --release --split-per-abi --obfuscate --split-debug-info=private-symbols/1.1.0
```

أدخل دومين السيرفر أو IP مع منفذ اختياري. HTTPS فقط مع شهادة موثوقة مطابقة للعنوان؛ شهادة الدومين لا تصلح تلقائياً لعنوان IP. يفحص التطبيق /mobile-config ثم يفتح /login داخل WebView نفسه. لا يحتاج CORS عاماً أو كلمة مرور مدمجة.

ملف التجربة: build/app/outputs/flutter-apk/app-debug.apk. لإصدار الإنتاج أنشئ android/key.properties من key.properties.example وأضف مفتاحك محلياً ثم نفّذ flutter build appbundle --release. البناء الإنتاجي يرفض غياب إعداد التوقيع ولا يستعمل مفتاح debug تلقائياً. راجع معرف الحزمة قبل تسجيله بالمتاجر.

iOS يحتاج macOS وXcode: افتح ios/Runner.xcworkspace بعد flutter pub get، واضبط فريق Apple ومعرف الحزمة. الحد الأدنى iOS 13. لا يمكن بناء أو إثبات سلوك WKWebView على Windows.

## MVC وGetX

| المسار | المسؤولية |
| --- | --- |
| lib/models | عنوان السيرفر ورسائل البروتوكول |
| lib/views | شاشة اتصال عربية RTL وWebView وحالات الخطأ |
| lib/controllers | GetX وإدارة التنقل والجلسة والإلغاء والطباعة والمشاركة |
| lib/services | HTTP مع Cookies الأصلية ومستند الطباعة المعزول |
| test | اختبارات العناوين والـorigin والبروتوكول والطباعة والواجهة |

## السلوك المنفذ

- حفظ عنوان السيرفر وفحص التوافق عند التشغيل؛ الحساب وCSRF والصلاحيات ونقل الجلسة تبقى على الموقع.
- مخزن Cookies دائم دون استخراج HttpOnly من JavaScript أو مسح Cookies عند كل تشغيل.
- PortalNative.postMessage(String) عبر WebMessageListener بقائمة origins محددة، والتحقق من مصدر الرسالة والإطار الرئيسي والأصل الحالي. لا توجد أوامر shell أو SQL.
- منع التنقل خارج السيرفر، وفتح الروابط الخارجية بالنظام بعد التأكيد. النوافذ الجديدة تُرفض.
- منتقي WebView الأصلي لرفع الصور وملفات النسخ مع FileReader، دون صلاحية وصول شاملة للملفات. التحقق النهائي من الملفات للسيرفر.
- طباعة النسخة المرسلة بعد إزالة المحتوى النشط وجلب موارد السيرفر بواسطة Cookies الأصلية وتضمينها محلياً. JavaScript معطل في مستند الطباعة وCSP يمنع الشبكة الخارجية.
- حد رسالة الربط 2 MiB، وموارد الطباعة 80 مورداً و24 MiB، والتنزيل 256 MiB. عملية أصلية واحدة في الوقت نفسه، و4096 معرفاً بحد أقصى دون تنفيذ المعرف مرتين خلال عمر التطبيق.
- تنزيل متدفق بطلب GET واحد دون HEAD أو probe أو إعادة تلقائية، وقراءة اسم الملف من Content-Disposition ثم فتح المشاركة الأصلية. إعادة التوجيه مسموحة للسيرفر نفسه فقط.
- PortalMobile.complete يستخدم jsonEncode. مهلة التطبيق 55 ثانية تسبق مهلة الموقع البالغة دقيقة؛ لا يعيد الطباعة تلقائياً. النجاح يعني فتح الواجهة الأصلية ولا يؤكد خروج ورقة من الطابعة.
- عنوان السيرفر يُحفظ مرة واحدة لكل تثبيت. لا توجد واجهة أو دالة لتغييره، وحتى تعذر الاتصال أو تلف القيمة لا يفتحان اختيار عنوان جديد تلقائياً. إعادة التثبيت أو مسح بيانات التطبيق من إعدادات النظام يبدآن إعداداً جديداً. النسخ الاحتياطي ونقل بيانات التطبيق معطلان على Android، وبيانات الاتصال والمتصفح مستثناة من النسخ الاحتياطي على iOS.
- الرجوع عبر سجل الموقع وتحذير الفاتورة باستخدام editorDirty، وتأكيد المغادرة. إيماءة الرجوع الخاصة بـWKWebView معطلة لإبقاء الرجوع تحت الحماية الأصلية.
- أخطاء الاتصال وHTTP بواجهة أصلية؛ التحقق من TLS للنظام دون أي تجاوز للشهادات.
- دعم HTTP Basic Auth ببيانات يدخلها المستخدم دون حفظ كلمة المرور على القرص أو إرسالها إلى origin آخر.
- الملفات المشاركة مؤقتة، وتُحذف بعد مرور يوم عند تشغيل التطبيق لاحقاً حتى يستطيع التطبيق المستلم قراءتها.

## مراجعة السيرفر

قُرئت Mobile_Web.py وAli_Mizan_Viewer.py وSite_Auth.py وDevice_Sessions.py وDatabase_Admin.py وموضع تحذير الفاتورة في Invoice_Entry.py. لم يُشغّل السيرفر ولم تُعدّل قواعد البيانات أو الحسابات.

- /mobile-config يعرّف business_portal وprotocol_version=1. هذا فحص توافق عام وليس إثبات هوية السيرفر أو صلاحية قاعدة البيانات.
- /login ينفذ تسجيل الدخول وتأكيد نقل الجهاز داخل الصفحة الأصلية.
- /database-admin-download?key=... هو مسار Content-Disposition الموجود حالياً. الموقع يمرره إلى PortalMobile.download؛ ويعترض التطبيق الانتقال المباشر إليه قبل استهلاكه بواسطة WebView.
- بصمات ملفات المشروع قبل الإضافة في server-hashes.json ونتيجة المقارنة في server-integrity-result.json.

أي مسار تنزيل جديد يجب أن يمر بقناة PortalMobile.download الموجودة أو يُضاف لاعتراض التنقل قبل الطلب. لا يعيد التطبيق جلب رابط عام وصل بالفعل إلى onDownloadStartRequest لأن ذلك قد يستهلك رابطاً أحادي الاستخدام مرتين. لا تُفتح هذه التنزيلات خارج التطبيق دون الجلسة.

## اختبار القبول قبل النشر

نجاح اختبارات Dart وبناء APK لا يثبت جميع وظائف WebView أو قبول المتاجر. يلزم اختبار Android وiPhone فعليين أمام سيرفر HTTPS تجريبي مستقل:

1. حفظ العنوان وإعادة التشغيل وتسجيل الدخول وتحديث الصفحة وبقاء معرف الجهاز.
2. رفع PNG/JPG وملف نسخة، وعرض صورة في فاتورة محفوظة ومسودة وطباعتها.
3. تنزيل نسخة مصرح بها مرة واحدة ورفض التنزيل غير المصرح.
4. نقل الحساب لجهاز آخر وإغلاق جلسة الجهاز السابق.
5. الرجوع من فاتورة معدلة وتغيير الاتجاه ولوحة المفاتيح وRTL.
6. رفض TLS غير الصالح وorigin آخر ورسائل إطار خارجي، وتجربة انقطاع الإنترنت.
7. إلغاء الطباعة والمشاركة وانتهاء المهلة وإعادة تشغيل التطبيق أثناء طلب جارٍ.
8. تجربة Basic Auth إن كانت البوابة مفعلة، وحسابات مراجعة مستقلة غير إدارية.

جهّز سياسة الخصوصية وتصريحات بيانات المتاجر وحسابات المراجعة وعنوان العرض قبل النشر. لا توجد حسابات أو بيانات اعتماد إنتاج داخل التطبيق.

توثيق المكتبات: https://inappwebview.dev/docs/webview/in-app-webview/ و https://github.com/pichillilorenzo/flutter_inappwebview و https://pub.dev/packages/share_plus
